## Sender and state observations

- `RsCommonV2Sender.setHearingProtection`, 0x881a54: rejects negative and >6; 0x881aa0 stores Dart Smi 0x8c (wire command 0x46), then boxes the requested value. `RsCommonV2Receiver._handleHearingProtection`, 0xf069fc: requires exactly one value byte (the original receiver operates on a two-character hex string), parses hex, and rejects values outside 0..6. V2 dispatch at 0xefd4cc delegates here when command string at pp+0x12988 is `46`.
- Original `DeviceHearingProtectionSlider.build`, 0xcc0714, clamps level to 0..6 and indexes pp+0x4b4c8. Its seven-element constant array ref 0x2a567 is `[null,75,80,85,90,95,100]`. Both that array and pp+0x4b4d0's matching subtitle keys were recovered with `array-recovered.json`'s already-validated cluster boundaries. Thus dB values are display labels; sending literal 75..100 would be incorrect. Decompilation is in `screenshot-hearing/dart/`; track clamp is in `screenshot-hearing-track/dart/`.
- `RsCommonV2Sender.setDingLevel`, 0x8fab34: rejects negative and >5; 0x8fab80 stores Smi 0x5c (wire 0x2e). Original Zircon config allocates `DeviceDingLevelPanelItemWidgetModel` at 0x6d2ccc. V2 dispatch at 0xefd20c handles pp+0x12900=`2e` by calling `F8Receiver._handlePromptToneLevel`, 0xefab94. This receiver parses the value and calls its receive handler; reconstruction additionally bounds it to the sender's 0..5 and one byte. Focused receiver output is in `screenshot-prompt/dart/`.
- `setFindDevice`, 0x7d2dd0, accepts 1..4 and stores Smi 0x5e (wire 0x2f). Named getters at 0x7d3028 / 0x7d2ee0 / 0x7d2da0 provide left=1 / right=2 / both=3. `get_setFindOff`, 0x7d2c48, writes 4, not 0.
- V2 dispatch at 0xefd2dc routes pp+0x12928=`2f` to `_handleEarFind`, 0xf08100, then `RsCommonV2ReceiveHandler.findMeReceived`, 0xea382c. The latter recognizes strings `01`..`06`: 1/2 enables the corresponding ear flag; 3 enables both plus group flag; 4 clears all flags; 5/6 clears just left/right. The protocol preserves the raw event in state.values[`find`] (1..6), and accepts only 1..4 for sending. Focused handler output: `screenshot-find/dart/`. It does not interpret an ACK as a confirmed setting.

## Implementation and verification

`ZirconProtocol.payload` and `apply` now support these three dedicated UI keys without adding them to the generic `controls()` list. The existing initialization query already includes 0x2e, 0x2f and 0x46, so no new probe was invented. The UI should treat find state as the last event rather than a complete left/right snapshot; 5 and 6 do not imply that both ears stopped.

`test.ps1`: PASS, 59 static protocol checks. Added 29 checks covering golden frames/checksum rollover, sender range rejection, exact reply lengths, reply range boundaries, repeated state, invalid-reply state preservation and receive-only find stop events. These confirm client encoding/decoding consistency with the static evidence, not firmware support or successful over-the-air execution.

Remaining unknown: actual firmware implementation/behavior of hearing protection and per-ear find events on this user's device; requires hardware validation. No approximation of unknown commands was added. Screenshot first-image controls appear consistent with these shared V2 commands, but its UI source itself was not supplied as source code.
